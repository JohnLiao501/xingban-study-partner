## 3. 已完成：隔离验收辅助

G3-A 已于 2026-08-31 完成。原下一步为真实 25 分钟场，现按 2026-09-03 决定延期到 N1～N4 之后；该批次只增加验收基础设施与同场重新授权入口，不改变正式产品判定语义。

### 3.1 隔离用户数据

- 验收启动时使用操作系统临时目录下的独立 `userData`，不读取或写入用户正式 SQLite、设置、历史和信赖。
- 目录名使用随机后缀，启动前解析并验证路径位于系统临时目录内。
- 正常退出会等待截图 renderer 的媒体轨停止回执与 sidecar 退出；外层启动器在中断时先对本次 Electron 精确 PID 树执行有界清理，确认子进程退出后才读取证据和删除目录。无法确认退出时门禁失败且不对仍活动的目录执行递归删除。
- 不使用删除正式数据库、清空历史或覆盖迁移来实现隔离。

### 3.2 本机脚本化 mock AI

- 只监听 `127.0.0.1` 的随机端口，不访问真实外网，不要求用户真实 API 密钥。
- 默认 5 步原始响应依次是：AI `focused`、高置信 `distracted/private_communication`、两次高置信 `distracted/entertainment_content`、AI `focused`；私人通讯由产品政策层降级为 `uncertain`，不是 mock 直接伪造最终标签。
- 只接受固定本机假令牌、`stage3-local-mock` 模型和不含窗口标题的严格请求形状；额外请求、错位、脚本耗尽或任何形状违规都计入失败。
- 请求体只在内存中解析和计数，响应后立即释放；不记录 JPEG、base64、目标、窗口标题、Authorization 或模型原始请求。
- mock/适配器测试覆盖超时、429、5xx 和无效 JSON；政策层既有测试另行覆盖标签/原因码语义矛盾，以上失败均由编排层安全降级为 `uncertain`。

### 3.3 确定性巡查与摘要

- 只在验收开关下使用固定种子和明确的巡查节点，正式模式继续使用现有随机调度。
- 输出仅包含时间点、状态、标签、原因码、偏航计数、流状态和通过/失败布尔值。
- 摘要不得包含截图、base64、完整目标、完整窗口标题、密钥或模型请求体。
- 自动化证明超时/协议失败安全降级、任何中断结果不能通过、精确目录清理单元和正常退出回执逻辑；真实 runner 的 SIGINT/SIGTERM 媒体流/进程树清理仍须在 G3-B/G3-G 留下桌面证据。

### 3.4 实现与预检证据

- `pnpm run acceptance:stage3:preflight` 验证固定节点 2:00、3:00、5:00、8:00、11:00、15:00、18:00，严格消费恰好 5 个 mock 请求；对一份安全文本文件执行不限 8 MiB 的流式扫描，确认无图片、data-image、JPEG base64、固定假令牌或符号链接，再删除精确目录。
- `pnpm run acceptance:stage3` 使用外层 Node 启动器创建随机临时目录和回环 mock，再启动 Electron。启动器要求恰好 8 条有序观察、由 15 秒定时器产生且持久化时间差不少于 14.5 秒的娱乐二帧、`active → stopped → active`、暂停/恢复、7 个巡查、1500 秒结算、B/29 信赖只写一次、无 BLOB/截图/base64/假令牌残留及正常退出清理回执；未满 25 分钟、中断、额外 mock 请求或任一证据缺失均返回失败。
- 主界面在停止共享后提供“重新授权屏幕”：必须由用户再次点击加载、选择 source，再由主进程校验活动会话、一次性 token 和源仍存在；不会复用旧授权或自动选择第一个屏幕。
- 隔离 Electron 短时冒烟已确认手工触发预览后可见窗口数 `1 → 2 → 1`，第二次变化发生在 6 秒复查时；中断后项目进程和验收临时目录均为 0。该项只覆盖真实自动隐藏，不替代 G3-B。
- 自动测试与浏览器 QA 不能证明真实屏幕流、真实前台应用切换或 25 分钟墙钟运行，因此 G3-B 仍未完成。

## 4. 真实 25 分钟人工场

该场使用原创 demo 伙伴、隔离用户数据和本机 mock AI。用户只需完成一次选源和一次重新授权；Agent 负责启动、观察、计时、结束、进程检查和隐私扫描。下列分钟数均指有效专注计时，暂停耗时不计入 25 分钟，因此实际墙钟时间可以略长于 25 分钟。

中途巡查结果和置顶悬浮窗会在 5 秒后自动收起并继续计时，无需返回主窗点击继续；只有达到计划时长后的结算/休息选择保留人工操作。若任一中途反馈持续遮挡或计时未自动恢复，本场立即判失败并修复，不要求用户绕过。

建议顺序如下，具体节点由会话面板提示给出，不依赖用户记忆：

1. 0～2:10：让允许进程保持前台；2:00 节点应 `focused`，不截屏、不调用 AI。
2. 2:10～3:30：尽快切到禁止进程并保持至少 20 秒；3:00 节点只记一次本地规则偏航，提前量包含用户反应与 5 秒采样余量。
3. 3:30～7:30：切到不匹配规则的窗口；5:00 节点由 mock AI 返回 `focused`。
4. 7:30～10:30：保持未知窗口；8:00 附近可能先出现五分钟恢复反馈，自动回流后私人通讯节点必须为 `uncertain` 且不扣偏航，低敏轨迹允许该节点延后至 8:05 内。
5. 10:30～14:00：保持同一未知窗口；11:00 首帧与至少 15 秒后的新帧都为高置信娱乐分心，只有第二帧确认后记一次 AI 偏航。
6. 14:00～16:00：从托盘或会话面板停止共享；15:00 节点只能安全降级，不产生迟到处罚。
7. 16:00～18:00：点击“重新授权屏幕”，再次加载并明确选择同一 source；随后暂停和恢复一次，暂停时间不计入专注时长。
8. 18:00～25:00：让允许进程保持前台；18:00 节点应 `focused`，随后完成会话并确认结算、评价、历史和伙伴信赖只写入一次。

通过条件：恰好两次预期偏航，其中一次来自连续本地禁止规则、一次来自 AI 两帧确认；全部 `uncertain` 不处罚；停止共享后无新帧；暂停计时正确；正常结算幂等；退出后 Electron、sidecar、mock server 和捕获流均为 0；临时验收目录删除前扫描无截图/base64，删除后目录不存在。

若应用随机时机、系统弹窗或人为操作使某个场景没有实际发生，本场记录为未完成而不是猜测通过。只补做缺失场景，不重复已取得的内容保护证据。

### 6.1 B0 的诊断边界

- 先复现并区分 Electron 主进程失败、renderer `launch-failed`、GPU 子进程缺失依赖和系统驱动/资源故障；不要把 `app.disableHardwareAcceleration()` 当作默认修复。
- 使用随机隔离 `userData`，每次启动后只确认设置界面可用，不请求屏幕权限、不读取正式数据库。
- 每次失败都必须等待启动器完成子进程退出、流/sidecar 停止、隐私扫描和精确目录删除，再进行下一次尝试。
- 若同一机器连续 3 次冷启动通过，记录为启动稳定性门槛通过；单次偶然成功不足以关闭 B0。

### 6.2 B1/B2 的协作方式

- 前台规则验收以真实 Windows 前台探针为准。窗口控制工具可辅助打开应用，但不能替代用户在真实桌面上的最终切换证据。
- B1 只验证最容易浪费整场时间的 2:00/3:00 两个本地节点；3:00 未命中时立即结束，不继续等待 22 分钟。
- B1 通过后才在同一环境执行 B2；B2 中用户只负责选源、真实前台切换、停止共享、重新授权与暂停恢复，Agent 负责计时、证据和清理。
- B2 的 UI 自动化只在设置阶段、14～18 分钟交互阶段及 25:00 后结算退出阶段临时关闭主窗/悬浮窗内容保护；1 秒后及 18:00 起自动恢复，截图专用窗口始终保护。既有内容保护专项证据仍独立有效。
- 任一固定节点与预期不符时停止本场并读取 `processMatch`、`localVerdict`、`localReason`；不凭视觉印象补记通过。

#### 根因一：Agent 外壳注入 `ELECTRON_RUN_AS_NODE=1`（已修复）

本仓库的自动化外壳环境中存在 `ELECTRON_RUN_AS_NODE=1`。该变量会让 Electron 可执行文件以**纯 Node** 运行：

- `process.type` 为 `undefined`，没有主进程、窗口、GPU 进程；
- `import { safeStorage } from "electron"` 解析到 npm 包 `index.js`（它只导出可执行文件路径），于是抛出
  `SyntaxError: The requested module 'electron' does not provide an export named 'safeStorage'`；
- `electron --version` 打印的是 Node 版本（`v24.18.1`）而不是 `v44.0.0`；
- 退出码常为 `0x80000003`。

修复方式是在生成子进程环境时显式删除该变量，而不是关闭硬件加速或改代码：
`scripts/diagnose-stage3-startup.mjs` 与 `scripts/run-stage3-acceptance.mjs` 均已通过 `buildChildEnvironment()` 剔除。
两个 runner 的判据也加入了 `runtime` 事件（`processType`、`isBrowserProcess`、`electronVersion`），
`isBrowserProcess !== true` 直接判失败，避免把“以 Node 运行”误记成通过。

#### 根因二：Electron 44 的 `loadFile()` 不对非 ASCII 路径编码（已修复）

工作区位于含中文的路径下。Electron 44 的 `BrowserWindow.loadFile()` 不会把路径百分号编码，
于是三个窗口（主窗、悬浮窗、截图窗）全部以 `ERR_FAILED (-2)` 失败，并连带引发 GPU 子进程反复崩溃，
外观上完全像 “renderer/GPU `launch-failed`”。

对照实验（同一台机器、同一 Electron 44.0.0）：

| 加载方式 | 结果 |
| --- | --- |
| `loadFile()` + ASCII 路径 | 成功 |
| `loadFile()` + 中文路径 | `ERR_FAILED (-2)` |
| `loadURL(pathToFileURL(p).href)` + 中文路径 | 成功 |

修复：`electron/main.ts` 的 `loadRenderer()` 改用 `pathToFileURL()` 生成正确编码的 `file://` URL 再 `loadURL()`；
`view` 参数通过 `searchParams` 追加，开发模式 `VITE_DEV_SERVER_URL` 分支保持不变。
该修复与路径是否为 ASCII 无关，属于生产构建下的真实缺陷。

#### 根因三：沙箱化外壳会杀死 GPU 进程（环境前提，非代码缺陷）

在受限沙箱中执行同一个诊断时，GPU 进程会以 `exit_code=1` 反复崩溃（约每 2 秒一次），
`child-process-gone` 持续上报 `GPU / killed / 1`，随后所有 `loadURL` 都返回 `ERR_FAILED (-2)`。
同样的脚本在真实桌面权限下运行，子进程崩溃数为 0。

因此这不是应用层缺陷，而是沙箱阻断了 GPU 与驱动访问。**B1 及之后所有真实 Electron 验收必须在非沙箱、真实桌面会话中执行**，
否则会把环境限制误判为产品失败。

### 6.5 B1 及后续真实验收的运行前提

1. 子进程环境不得包含 `ELECTRON_RUN_AS_NODE`（两个 runner 已自动剔除；手工 `pnpm start` 前需 `env -u ELECTRON_RUN_AS_NODE`）。
2. 必须在非沙箱、真实桌面会话中执行；沙箱内 GPU 进程必崩。
3. 每次运行前确认无残留 `electron.exe` 与 `windows-foreground-probe.exe`。
4. 先跑一次 `pnpm run diagnose:stage3:startup --runs=1` 确认能复现 B0 的绿色结果，再进入 B1。
5. 不得用 `app.disableHardwareAcceleration()`、缩短连续判定时间或改动固定节点来换取表面通过。
